# Page-by-Page Testing Progress

Tracks the live-stack Playwright testing phase (started 2026-07-27): one sidebar
page at a time — audit frontend + backend for hardcoded/fabricated/dead data
and broken routes, fix real bugs found, write `tests/e2e/<page>.spec.ts`
against the real backend + seeded DB, verify `go build`/`go vet`/`go test` +
`tsc`/`lint`, run the full accumulated suite, update this file and the
project memory (`project_page_testing_phase.md`).

**How to use this file**: read it at the start of a session to see what's
next; update the relevant checklist line(s) at the end of every page (move
from ⬜ to ✅ with a one-line summary + spec file name). Full detail for each
page lives in memory (`project_page_testing_phase.md`), not here — this file
is just the index/checklist.

Full suite status as of last page (Threat Intel): **170/179 passing**, 5
failures, all matching already-documented flake classes and none touching
this page's files (`intel_enterprise.go`, `threat-intel/page.tsx`,
`threat-intel.spec.ts` — this page's own 5 tests all passed): the
pre-existing agents.spec.ts race, the pre-existing Network Map canvas-click
race, and 3 local-LLM-contention timeouts.
**Growing self-inflicted flake class — escalating, worth addressing soon**:
this phase now has **5** CPU-bound local-LLM tests spread across 4 spec
files (`elastic-query.spec.ts` ×2, `log-sources.spec.ts` ×1,
`clusters.spec.ts` ×1, `threat-intel.spec.ts` ×1 — each 20-90s+ on this
machine's GPU-less Ollama) that can contend with *each other* under
full-suite parallelism; this run's failures include `clusters.spec.ts`'s
AI test timing out at a full 120s budget for the first time (previously
always passed standalone) purely from this contention. Every one of the 5
has independently passed cleanly in isolation/small batches, so a solo
failure among them under a big parallel run is still this known class, not
a regression — but the count keeps growing as more AI-backed pages get
tested, and it may be worth proposing a real fix (e.g. tagging these tests
to run serially relative to each other, or in a separate low-concurrency
project) before it gets worse. A mid-session memory-pressure incident
(swap in use, load avg 7-11) was resolved by restarting the long-running
`next dev` process — same "restart before assuming a real regression"
lesson as the Attack Paths incident earlier this phase.
**Infra note**: this dev environment had no working LLM at all this session
(`.env` said `LLM_PROVIDER=ollama` but Ollama was never installed) — every
AI-backed endpoint app-wide was silently returning "AI service unavailable".
Installed Ollama + pulled `qwen2.5:3b` (matching `.env`'s `OLLAMA_MODEL`) to
unblock testing; it's slow (30-90s/call, CPU-only) but functional. If AI
features on a future page seem broken, check `ollama list` /
`curl localhost:11434/api/tags` first, not the page's code.
